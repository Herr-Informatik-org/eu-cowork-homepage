Konfiguration

EU Cowork AI wird an drei Stellen konfiguriert. Wer weiss, welche Stelle wofür zuständig ist und welche Ebene bei einem Widerspruch gewinnt, spart sich das Suchen. Diese Seite ordnet die Ebenen ein und listet die Werte auf, die im Alltag wirklich gebraucht werden.

Die drei Ebenen

Abschnitt betitelt „Die drei Ebenen“
Ebene Datei oder Ort Inhalt Wann es wirkt
Infrastruktur und Geheimnisse distribution/.env Ports, Domains, Schlüssel, Bindungen, Profile-Werte nach docker compose up -d
Produktverhalten distribution/librechat.yaml Modellkarten, Oberfläche, Konnektoren, Registrierung nach Neustart des Dienstes api
Laufzeit-Overrides Admin-Panel, Seite Konfiguration dieselben Produkteinstellungen, pro Instanz, Rolle oder Gruppe sofort, ohne Neustart

Welche YAML-Datei aktiv ist, entscheidet LIBRECHAT_CONFIG_FILE in der .env. Standard ist librechat.yaml, das Kundentemplate. Daneben liegt librechat.internal.yaml als Beispiel für eine Instanz mit angebundenen Konnektoren. Alle Aussagen dieser Dokumentation beziehen sich auf das Kundentemplate.

Welche Ebene gewinnt

Abschnitt betitelt „Welche Ebene gewinnt“

Ein im Panel gesetzter Wert steht über der YAML. Das Panel schreibt seine Werte in die Datenbank, LibreChat liest sie beim nächsten Aufruf und sie überleben einen Neustart. Die YAML bleibt der Ausgangszustand, der greift, solange kein Override existiert.

Im Panel erkennen Sie das an zwei Details: Abschnitte mit aktivem Override tragen den Badge aus DB-Override, und neben jedem überschriebenen Feld gibt es ein Symbol zum Entfernen.

Ein Feld zu leeren entfernt den Override nicht

Wer ein überschriebenes Feld im Panel leert, speichert einen leeren Wert und behält den Override. Zurück zum YAML-Stand kommen Sie nur über das Rücksetz-Symbol neben dem Feld.

Für Modellkarten gilt zusätzlich eine eigene Kaskade: Gruppe vor Rolle vor Basis. Die Rechte an Werkzeugen gehören dagegen in den Rollen-Editor und nicht in die Konfiguration, im Reiter Funktionen würden sie serverseitig verworfen.

Die vollständige Liste mit Kommentaren steht in distribution/.env.example.

DISABLE_COMPRESSION nicht auf false stellen

LibreChat schreibt seine Antworten als Strom, ruft dabei aber kein res.flush() auf. Mit aktiver Kompression puffert der Server deshalb die ganze Antwort bis zum Ende. Clients mit Zeitlimit, allen voran die Ansicht des Outlook-Add-ins, brechen dann bei langen Antworten ab. Caddy komprimiert für Browser weiterhin, es entsteht also kein Nachteil.

Compose-Profile

Abschnitt betitelt „Compose-Profile“

Ohne Profil startet der Basis-Stack: Chat, Admin-Panel, Outlook-Add-in, MongoDB, Meilisearch und SearXNG. Jedes Profil schaltet weitere Dienste dazu.

Profil Schaltet zu
production Caddy als Reverse-Proxy mit automatischem TLS auf Port 80 und 443
filesearch Vektordatenbank und RAG-Dienst für die Suche in hochgeladenen Dateien
internal MCP-Gateway und die Beispiel-Konnektoren, die darüber laufen
microsoft Beispiel-Brücke zu einer Dateiablage mit Anmeldung pro Person
interim Das alte Admin-Panel unter AGPL, reine Übergangslösung

Profile werden bei jedem Aufruf mitgegeben. Wer den Stack später ohne die Profile neu startet, stoppt die zugehörigen Dienste nicht, startet sie aber auch nicht neu. Führen Sie deshalb Update und Neustart immer mit derselben Profilliste aus, mit der Sie installiert haben.

Der interface-Block

Abschnitt betitelt „Der interface-Block“

Der Block steht in der aktiven YAML-Datei und steuert, was in der Oberfläche sichtbar ist. Das sind die Schalter, die im Kundentemplate tatsächlich gesetzt sind:

Schalter Standard Wirkung
customWelcome gesetzt Begrüssungstext auf der Startseite des Chats
mcpServers.use true Mitarbeitende dürfen die vom Admin definierten Konnektoren nutzen
mcpServers.create false Niemand ausser dem Admin legt eigene Konnektoren an
mcpServers.share false Konnektoren werden nicht von Person zu Person geteilt
webSearch true Der Knopf für die Web-Suche ist sichtbar
fileSearch false Suche in hochgeladenen Dateien, braucht das Profil filesearch und einen Embeddings-Anbieter
runCode false Code-Ausführung, braucht ein Backend hinter LIBRECHAT_CODE_BASEURL
remoteAgents.use true Agenten dürfen von aussen angesprochen werden, Voraussetzung fürs Outlook-Add-in
remoteAgents.create false Agenten werden in der Oberfläche gepflegt, nicht über die Schnittstelle angelegt
parameters false Das Parameter-Panel für Temperatur und Ähnliches bleibt verborgen
modelSelect true Der Modell-Picker mit den kuratierten Karten ist sichtbar

fileSearch und runCode sind bewusst aus, solange ihr Backend nicht läuft. Ein sichtbarer Knopf ohne Wirkung ist schlechter als kein Knopf. Sobald das Profil filesearch läuft und ein Embeddings-Anbieter eingetragen ist, setzen Sie fileSearch: true, für die Code-Ausführung entsprechend runCode: true.

Web-Suche im Kundentemplate

Der Knopf ist sichtbar und die eigene Metasuchmaschine läuft im Stack. Es fehlt aber noch der Scraper, der die Trefferseiten ausliest. Solange er nicht konfiguriert ist, hängt LibreChat das Such-Werkzeug nicht an das Modell, die Suche löst also nicht aus. Konfiguriert wird das im Panel unter Konfiguration im Reiter Funktionen.

Regel 1: Der Block ist global

Abschnitt betitelt „Regel 1: Der Block ist global“

Die Werte werden beim Start in alle Rollen geschrieben und bei jedem Neustart erneut gesetzt. Ein Unterschied zwischen Rollen lässt sich in der YAML deshalb nicht abbilden. Wollen Sie ein Werkzeug nur für eine Rolle freigeben, lassen Sie das Feld aus der YAML weg und setzen es im Rollen-Editor des Admin-Panels. Genau darum stehen Skills und Agenten bewusst nicht im interface-Block.

Regel 2: capabilities ersetzt, statt zu mischen

Abschnitt betitelt „Regel 2: capabilities ersetzt, statt zu mischen“

Welche Fähigkeiten es überhaupt gibt, legt endpoints.agents.capabilities fest. Artifacts, also Diagramme und HTML direkt im Chat, sind ausschliesslich dort steuerbar, ein interface.artifacts gibt es nicht. Wer die Liste anfasst, ersetzt die Standardliste vollständig. Es wird nichts zusammengeführt, alles Behaltene muss also erneut aufgezählt werden.

KMU-Einfach-Profil

Abschnitt betitelt „KMU-Einfach-Profil“

Für Unternehmen, die eine möglichst schlichte Oberfläche wollen, schalten Sie die Bedienteile ab, die nur Poweruser brauchen. Alle Felder unten sind im Kundentemplate als Vorlage vorhanden:

Was das bewirkt:

  • modelSelect: false blendet den Modell-Picker aus. Alle arbeiten dann mit der Standardkarte samt hinterlegtem Systemprompt, ohne selbst ein Rohmodell wählen zu können.
  • presets: false entfernt die Voreinstellungen, multiConvo: false die parallelen Chats, bookmarks: false die Lesezeichen und marketplace.use: false den Werkzeug-Marktplatz.
  • parameters: false hält das Parameter-Panel verborgen. Soll der Admin es trotzdem sehen, bekommt die Rolle ADMIN im Panel einen Override auf interface.parameters.

Domain-Lock

Abschnitt betitelt „Domain-Lock“

Der Domain-Lock ist der erste Schritt nach der Installation und gehört gesetzt, bevor die Instanz unter ihrer Domain erreichbar ist. Massgeblich ist dabei nicht ALLOW_REGISTRATION, sondern die Liste der erlaubten E-Mail-Domänen: Sie entscheidet, wer überhaupt ein Konto anlegen kann.

Dieselbe Liste pflegen Sie im Panel unter Konfiguration im Reiter Funktionen im Feld Erlaubte E-Mail-Domains. Sie gilt für die Selbstregistrierung und für Einladungen: eine Einladung an eine Adresse ausserhalb der Liste greift nicht.

Prüfen lässt sich das mit einer Registrierung unter einer fremden Domäne, sie muss abgelehnt werden. Damit Sperren aus dem Panel überhaupt greifen, muss zusätzlich BAN_VIOLATIONS=true in der .env stehen.
