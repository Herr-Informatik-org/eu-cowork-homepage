Services and ports

This page lists every container of the Compose stack with image, task, port and profile. It is meant for looking things up, for example when you are writing a firewall rule or want to know why a service did not start.

All container names carry a prefix from the variable STACK_NAME, which defaults to eucowork. The container of the chat is therefore called eucowork-api by default.

The services

admin-panel AGPL panel of LibreChat transitional tool, not part of the product host ${ADMIN_PANEL_PORT}, default 3000 interim

The bridges of the internal profile run through the gateway and each hold their own service account in the third party system, whose permissions there form the actual authorization boundary. The bridge of the microsoft profile deliberately bypasses the gateway, because there every person signs in individually. How such a bridge is put together and which parts belong to it is described by the connector pattern.

Pin images to a digest for production

The LibreChat image is pinned to a digest so that the same verified version runs on every server. searxng, rag_api and the interim panel admin-panel sit on :latest and may fetch a newer build on a docker compose pull. For a reproducible installation, pin those three to a digest as well in distribution/docker-compose.yml and make changing the digest part of your update procedure. Why a fixed digest is the better choice is explained under Updating.

Which ports belong to the outside

Section titled “Which ports belong to the outside”

Only three: 22, 80 and 443. Everything else stays local.

Port Service Reason
22 SSH administration
80 Caddy issuance of the certificates and redirect to HTTPS
443 Caddy chat, admin panel and Outlook add-in

Caddy is the only service that may listen on all interfaces. The admin panel and the Outlook add-in are already bound to 127.0.0.1 out of the box. The database, the search index, the gateway and all connector bridges are not published on the host at all, they are reachable exclusively on the internal Docker network.

Two points you have to take care of yourself:

  • The chat port is bound to 0.0.0.0 by default. In production API_BIND=127.0.0.1 belongs in the .env, otherwise LibreChat is reachable unencrypted at <server-ip>:3080, bypassing Caddy and TLS.
  • The transitional panel of the interim profile binds to all interfaces. It is a test tool and does not belong on a reachable server.

The firewall does not take effect on Docker ports

Ports published by Docker through ports: bypass ufw, because Docker writes its own iptables rules into the DOCKER-USER chain. A container bound to 0.0.0.0 is reachable from the outside despite an active firewall. The protection lies in binding to 127.0.0.1, not in the firewall rule.

The Docker networks

Section titled “The Docker networks”

The stack uses two networks.

Network Type Who is in it
default bridge with a fixed subnet from DOCKER_SUBNET, default 172.28.0.0/16 all services of the stack
sandbox external network from SANDBOX_NETWORK, default eucowork-sandbox only api, plus the separate code interpreter stack

The sandbox network is deliberately created outside the stack, so that both Compose projects can start and stop independently of each other. install.sh creates it. If it is missing, Compose reports on startup that the network declared as external cannot be found. The command for it:

The fixed subnet is intentional. If it collides with a route that a VPN pushes onto the machine, the outbound connections of the containers break. In that case enter a free range in DOCKER_SUBNET in the .env.

Several instances on one machine

STACK_NAME, DOCKER_SUBNET and SANDBOX_NETWORK apply across all of Docker and therefore have to be unique per instance. The same applies to the host ports PORT, ADMIN_SIDECAR_PORT and OFFICE_ADDIN_PORT. In the worst case, two instances on the same sandbox network would end up in the code interpreter of the other customer.

Health checks

Section titled “Health checks”

Only the connector bridges of the internal profile have health checks. They query their own health endpoint every 30 seconds, with a five second timeout and three attempts. The start period is 15 to 20 seconds depending on the bridge.

All other services have no health check. In docker compose ps they therefore appear as Up without a health status, which is not an error. Whether the application really started cleanly is visible in the log:
