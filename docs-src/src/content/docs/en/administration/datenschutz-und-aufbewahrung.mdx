This page states as precisely as possible which data stays for how long, how you provide a disclosure or carry out a deletion and what the installation sends outward. It deliberately also contains what is not there.

## The retention period

Under **"Einstellungen → Aufbewahrung"** (settings, retention) sits the card **"Aufbewahrung (Retention)"** (retention) with the field **"Aufbewahrung in Tagen"** (retention in days).

| Property | Value |
| --- | --- |
| Permitted range | 1 to 3650 days |
| Field empty | Retention is off, nothing is deleted automatically |
| Decisive | the last change to the conversation, not the date it was created |
| When deletion happens | in a daily run |

What is deleted are **conversations including their messages and the shared links created for them**, and permanently at that. What is not deleted is the **billing data**, meaning the transactions of usage metering. The usage of a past month therefore stays traceable even when the associated chats are long gone.

<Aside type="caution" title="Every shortening asks back">
If you set or shorten the period, a confirmation prompt appears. It names the old and the new period and points out that the shorter period will permanently delete additional, older conversations on the next run. You confirm with **"Frist setzen"** (set period). Extending it brings nothing back, what is already deleted stays deleted.
</Aside>

The button **"Jetzt ausführen"** (run now) appears as soon as a period is set and triggers the run immediately, likewise with a confirmation prompt. Below the field it states when the last run was, whether it was triggered automatically or manually and how many conversations and messages it removed.

## Disclosure and deletion per person

You reach both from the user list. The order is not arbitrary.

<Steps>

1. **Export.** The button **"Daten exportieren (JSON)"** (export data as JSON) delivers all data of this person as one JSON file: account, groups, credit balance, conversations, messages, file metadata and transactions.

2. **Delete.** Only afterwards delete. After the deletion no disclosure can be given any more, which is why the export button also sits directly in the deletion dialog in the block **"Erst exportieren, dann löschen"** (export first, then delete).

</Steps>

Two points about the export:

- **Files are included as metadata, not as content.** The actual files sit in the upload directory of the stack. Including them would turn the export into a file server.
- **Credentials are deliberately not included**, so neither the password hash nor two factor secrets nor the encrypted API keys stored for that person.

In the deletion dialog, the checkbox **"Auch Verbrauchs-Transaktionen löschen"** (delete usage transactions as well) decides the depth:

| Choice | Result |
| --- | --- |
| unticked | Account, conversations, messages, files, keys, agents and credit balance disappear. The transactions remain as a billing receipt. |
| ticked | additionally the transactions. This is the full GDPR deletion, and the **billing receipts are lost** in the process. |

In both cases you confirm by typing the email address exactly.

## Telemetry

The shipped state switches telemetry off. Two values in the `.env` are responsible for that:

| Variable | Effect |
| --- | --- |
| `MEILI_NO_ANALYTICS=true` | Meilisearch, the full text search across the conversations, sends no usage data to its maker |
| `NO_INDEX=true` | Search engines do not index the interface |

Both are set to `true` in the shipped state. If you take over an existing installation, check this once.

## Where the data sits and what leaves the stack

The installation runs entirely on your machine. Conversations and messages sit in the MongoDB of the stack, the search index in Meilisearch, uploaded files in local volumes. Of all the services, only the reverse proxy Caddy publishes ports outward; everything else is limited to the local interface or to the internal Docker network. Where this machine physically stands is decided by your choice of hoster.

Two things inevitably leave the stack, and you should know them and communicate them internally:

**Model requests go to the configured provider.** A language model computes where it is operated. In the shipped state that is EuRouter with processing in the EU. If you additionally connect providers outside the EU, the requests of those cards go there. There is no mode in which a cloud request does not leave the machine. Locally operated models are the exception, but they need suitable hardware.

**Web search requests go to external search engines.** The search runs through the self hosted SearXNG in the stack. SearXNG is a meta searcher, it forwards the search query to external search engines, though **without the identity of the person searching**. The queries themselves therefore do leave the stack.

<Aside type="caution" title="Say it precisely">
The honest formulation is: storage and inference can be kept in the EU or in Switzerland. With web search the search text leaves the building, only without any link to the user. The statement "with web search everything stays in the EU" would be wrong, and it comes back at you the first time somebody asks a critical question.
</Aside>

## Marking providers outside the EU

Providers that are not EU resident are marked as such in the panel and in the chat, so that the choice is made deliberately. This affects in particular model cards through OpenRouter, whose visible label carries the note "Nicht-EU" (non EU). The same rule applies to connectors: a connector whose target system is operated outside the EU has to be marked and does not belong in a customer deployment unasked.

Also note that the origin information in **"Provider-Routing"** (provider routing) comes from the provider and that the registered office of a provider is no guarantee of the place of processing. More on that under [Models and model cards](/docs/en/administration/modelle-und-karten).

## What does not exist

**No SCIM.** There is no automatic provisioning and no automatic deactivation of accounts from the identity provider. Accounts come into being at the first login through OIDC, and deprovisioning runs through the identity provider: whoever is deactivated there does not get through the sign-in any more and therefore reaches no data. For the complete removal of an account including its data, use the deletion dialog in the panel.

**No automatic billing.** Receipts yes, payment integration no. Details under [Usage, budgets and billing](/docs/en/administration/verbrauch-und-budgets).

**The hardened sandbox runner with an egress allowlist is not finished yet.** For code execution an interim backend currently runs. That is the largest known open point, and it is named here deliberately instead of being concealed.
