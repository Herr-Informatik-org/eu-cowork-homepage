For a customer with only a few people, a dedicated virtual machine is a waste: the baseline load
of an instance is low. Several instances may therefore share one machine. This page describes
where the dividing line runs. It is aimed at IT service providers who operate several customers.

## The tenant boundary is the instance, not the machine

A customer is exactly **one instance**: its own database, its own full-text search, its own
uploads, its own configuration, its own secrets, its own backend for code execution. That is not
negotiable and follows directly from the architecture: the application itself knows no tenants.
The separation therefore has to sit below the application, and there it sits cleanly.

Whether two instances share the same machine is then a question of cost and risk, no longer an
architectural one.

## What is never shared

| Area | Reason |
|---|---|
| Database | Contains accounts, conversations and bookings of a customer |
| Uploads and images | Customer content |
| Configuration and all secrets | A shared secret cancels out every separation |
| Backend for code execution | The only place where code from users runs |
| Inference key | With a shared key, costs per customer can no longer be broken out |
| Own meta search engine | Sees the search queries and thereby user content |

## What may be shared

- **Docker images and their layers.** That is the biggest saving: the images are held only once.
- **An upstream reverse proxy** as the only service holding the public ports.
- **Host monitoring, backup scheduling and automatic security updates.**

Kernel, Docker service and the hardware resources are inevitably shared as well. That is the
real limit of this way of operating: a reboot for a kernel update hits every customer on the
machine.

<Aside type="caution" title="Code execution is the hard part">
Everywhere else the platform only runs its own code; users have no access to the command line.
The exception is code execution. It therefore gets its own separate backend per instance. On a
shared machine the hardened variant is the better choice as well.
</Aside>

## What has to be unique per instance

Several instances on one machine collide if they share names or addresses. Every instance
therefore needs its own project and data area as well as its own network and port assignments.
Which values these are in detail and how they are set is described in the operations manual. If
they stay on their defaults, the second instance does not start.

## When a dedicated machine

- **Small customers:** several instances on a shared machine, depending on size three to five
  customers.
- **Medium customers:** a dedicated machine per customer.
- **Large customers, regulated industries, contractually guaranteed dedicated infrastructure or
  a dedicated ERP connection:** a dedicated machine sized accordingly.

The concrete guide values for memory, CPU and disk space are under
[System requirements](/docs/en/erste-schritte/systemanforderungen).

## Operating several instances

- **Backup per instance.** Every instance backs up exactly its own data, at staggered times.
- **Update per instance.** Customers may run different versions. That is exactly what the pinned
  versions are for, see [Updating](/docs/en/betrieb/aktualisieren).
- **Monitoring.** The first limit is disk space, not memory. An alert from 70 percent usage makes
  sense, as does monitoring for services that restart.
- **Offboarding.** Stop the instance, take an archive, delete the data. No intervention in other
  instances, no cleanup in a shared database. That is the real gain of the instance boundary.
