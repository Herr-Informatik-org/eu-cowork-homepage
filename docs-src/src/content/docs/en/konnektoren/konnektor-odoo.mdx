With this connection the chat answers questions about customers, documents, projects, staff, and time tracking straight from your Odoo. This page describes the setup, the installation, and the one operating rule you must not forget.

<Aside type="note" title="Not part of the shipped state">
The Odoo connection is not included in the customer template. It is part of the internal configuration and is deliberately switched on per instance. The shipped state of a new installation contains **no** preconfigured connector.
</Aside>

## How the connection is built

The most important point first: **the Odoo module does not speak MCP itself.** The module `mcp_server` from the Odoo app store merely provides its own routes under `/mcp/*`, secured by an API key in the header of the request and working internally against Odoo's ordinary interface. A chat system cannot do anything with that.

That is why a **bridge** runs in between, a small service of its own that speaks MCP on one side and Odoo on the other. For this we use the ready-made image `ivnvxd/mcp-server-odoo`, pinned to version `0.7.1`. The chain looks like this:

```text
Chat layer
  → MCP gateway            permission check per call, logging
    → Odoo bridge          holds the API key, translates MCP into Odoo's interface
      → your Odoo          enabled models, permissions and record rules of the key's user
```

The bridge has **no sign-in procedure of its own** and holds the API key. That is why it lives exclusively on the internal Docker network and never gets a port on the host. Access control is done by the gateway in front of it.

## Three instances, three service accounts

**Three instances of the same bridge** run side by side: `odoo-administrator`, `odoo-admin`, and `odoo-technik`. They are technically identical and differ in exactly one point: each uses its **own Odoo API key**, and each of those keys belongs to its **own Odoo user**.

That is the core of the concept. An API key in Odoo fully inherits the permissions and the record rules of its user. **The Odoo user behind the key is therefore the actual permission boundary**, not the prompt and not the configuration. If an Odoo user is not allowed to see a payslip, then the chat does not see it through that key either, no matter what the model tries.

Three instances instead of one therefore mean three permission profiles you can choose between per person. The gateway decides who sees which instance.

| Instance | Intended for |
|---|---|
| `odoo-administrator` | the widest profile, for example management |
| `odoo-admin` | the commercial profile |
| `odoo-technik` | the technical profile without the commercial view |

Which permissions these three actually have is something you define in Odoo, not with us. The names are only labels.

## Required variables

All values belong in `distribution/.env` on the server. That file is excluded from version control and is set to `600` by the installer. Only the names appear here, never values:

| Variable | Purpose |
|---|---|
| `LIBRECHAT_CONFIG_FILE` | selects the configuration file in which the connectors are defined |
| `ODOO_URL` | the base address of your Odoo |
| `ODOO_DB` | the name of the Odoo database, deliberately not detected automatically |
| `ODOO_MCP_API_KEY_ADMINISTRATOR` | key of the first service account |
| `ODOO_MCP_API_KEY_ADMIN` | key of the second service account |
| `ODOO_MCP_API_KEY_TECHNIK` | key of the third service account |

Alternatively the three keys can be stored in the admin panel under **"Einstellungen → API-Schlüssel"** (settings → API keys). They are write only there, so they are never displayed again. The sidecar writes them into exactly this `.env`. After that the bridges have to be restarted, because they read their key at startup.

## Setup

<Steps>
1. **Create three Odoo users** and give each one the permission profile you want. Then generate one API key each under **"Einstellungen → Benutzer & Unternehmen → Benutzer"** (settings → users and companies → users), select the user, tab **"API-Schlüssel"** (API keys), **"Neu"** (new).

2. **Release the reachable models** under **"Einstellungen → MCP Server → Enabled Models"** (settings → MCP server → enabled models), separately for read, write, create, and delete.

   This release applies **instance wide**, so it does not distinguish between your three service accounts. That distinction is made solely by the permissions and record rules of the three Odoo users.

3. **Enter the values in `distribution/.env`**, see the table above.

4. **Start the stack with the matching profile:**

   ```bash title="On the server"
   cd ~/eu-cowork/distribution
   docker compose --profile internal up -d
   ```

5. **Check that the three bridges are running.** All three have a built in health check, `docker compose ps` shows the state. In more detail it works like this:

   ```bash title="On the server"
   docker compose logs -f odoo-mcp-administrator odoo-mcp-admin odoo-mcp-technik
   docker exec eucowork-odoo-mcp-administrator python -c "import urllib.request;print(urllib.request.urlopen('http://localhost:8000/health',timeout=3).read())"
   ```

   The prefix `eucowork` in the container name comes from the variable `STACK_NAME`. If more than one instance runs on the machine, the containers carry a different prefix.

6. **Set the permissions, immediately.** Admin panel → **"MCP-Zugriff"** (MCP access), for **each** of the three instances set **"Server-Standard"** (server default) to denied and save. Then grant access deliberately to roles, groups, or individual people.

7. **Restart the chat layer**, so that the tool catalog is updated:

   ```bash title="On the server"
   docker compose restart api
   ```
</Steps>

<Aside type="danger" title="Grant exactly one instance per person">
All three instances expose **identical tool names**. If a person is granted two instances, the same tool catalog ends up in every conversation twice. That costs double context tokens on every message, and the model has to guess between two identically named tools, which leads to wrong calls.

So grant **exactly one** Odoo instance per person. If someone needs a different profile, switch the grant instead of adding a second one.

Also keep in mind that the gateway lets everyone through when there is no rule document. As long as "Server-Standard" (server default) is not set to denied, everyone sees all three instances.
</Aside>

## Which tools there are

The tools of this connection come from the **third party image**, not from us. Their exact names and their scope therefore depend on its version, and we deliberately do not document them here, because they can change with a version change.

You can see the tools that actually exist in two places. First in the connection test under **"Konfiguration → MCP-Server"** (configuration → MCP servers), which reports the count. Second, as soon as they are used, in the panel under **"System → Audit-Log"** (system → audit log), tab **"MCP-Tool-Calls"**, column tool. For every call it shows which tool was called by whom with which decision.

Functionally the connection covers the usual ERP objects: customers, documents, projects, staff, and time tracking. The approach in the chat has several steps: first search for the record, then read it specifically. That is laid down in the server instructions, together with the rule that write actions are always presented to the person for confirmation first.

## Recommendations for operation

**Keep the enabled models read only.** That is the sharpest and at the same time the simplest boundary. A tool can only do as much as Odoo has released for that model. If write, create, and delete are not ticked there at all, no model and no prompt can change that. Only enable write permissions for individual models where you really have the use case.

**Draw the data boundary in Odoo, not in the prompt.** Tools of this kind often accept free form filter expressions. A restriction at argument level is therefore not reliably enforceable. What is reliable are the record rules of the Odoo user behind the key.

**Use the log.** Every call through the gateway is written down immutably, with no deletion period. That makes it possible to prove afterwards who queried which ERP data and when.

**Bear in mind that Odoo does not know the individual chat user.** Everyone with the same granted instance sees the same thing, namely what the respective service account sees. If you need a finer separation, the way to get it is not an additional filter in the chat, but another Odoo user with narrower permissions and another instance of the bridge.
