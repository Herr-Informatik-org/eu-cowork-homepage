One of your own systems is attached as a connector: a service that offers a manageable number of tools and calls the interface of your system behind them. It is created and granted in the admin panel, without access to the server.

<Aside type="note" title="The step-by-step guide ships with your instance">
Along with your instance you receive a guide that describes the path from creating a connector to granting access step by step, matching your installation. This page deliberately stays one level above that: what to settle beforehand, how to measure a connector, and what you must not forget when granting access.
</Aside>

## What to settle beforehand

- **The technical name.** The connector runs under this name in your instance. It cannot easily be changed later. So pick something meaningful and durable.
- **The address where the connector speaks MCP.** The service has to be reachable from your instance.
- **The credentials for the target system.** They never belong in the configuration in plain text, only ever as a reference to a stored key.
- **The account behind the credentials.** It is the actual data boundary. In the target system, give it exactly the permissions and exactly the areas the use case needs, see [connector patterns](/docs/en/konnektoren/muster).
- **A short guide in prose** about when this tool should be used and what it cannot do. It is only inserted when the connector is active, and it noticeably improves the hit rate.

## Where do I get an MCP server for my system

**Ready-made servers exist for many products.** Because MCP is an open standard, vendors and communities publish connectors for common software. Search for the product name together with "MCP server". For systems with a programming interface of their own, chances are good that someone has already built the bridge.

**You can build one yourself.** A connector is a small service that offers a handful of tools and calls the interface of your system behind them. For a limited purpose, for example "five read queries against our line of business application", that is manageable. A deliberately narrow bridge is far cheaper in context than a ready-made server with a hundred tools.

**Review a third party server before you connect it.** A connector gets access to your data, that is not a formality. Four questions:

1. **Which tools does it expose?** Read the list in full. Writing tools you do not need are pure risk, and they cost context on top.
2. **Is there a read only mode?** A switch that disables write access in the code is worth considerably more than the intention not to use it.
3. **Is it suitable for multiple users?** Connectors that remember state across several calls do not work reliably in multi user operation.
4. **Where do the credentials live, and what is the license?** A connector that holds keys itself belongs on the internal network and nowhere else.

The outcome of such a review can very well be "we build it ourselves", especially if a ready-made server offers reboots, script runs, or write access alongside reading and that cannot be switched off. How a narrow bridge is cut is described under [connector patterns](/docs/en/konnektoren/muster).

## Granting access is a step of its own

A connector that has been created is not yet a connector that has been granted.

<Aside type="danger" title="Set the default rule to denied in the same work step">
Set the connector's **default rule** to denied before you do anything else. Then deliberately grant access to the roles, groups, or people who need the connector. How the decision comes about is described under [permissions and grants](/docs/en/konnektoren/gateway-und-rechte).
</Aside>

Finally, check the grant with two test users who have different permissions. If both see the same thing, your permission boundary is not taking hold.

## When something does not work

- **A tool reports "access denied".** That is not an error, that is the permission rule. Check the grants for the person concerned, see [permissions and grants](/docs/en/konnektoren/gateway-und-rechte).
- **The connector does not answer.** First check whether the service is reachable from your instance, then check the stored credentials for the target system.
- **The individual checks** are described in the guide that ships with your instance. It also covers the connection test, which checks a connection independently of the permissions.
