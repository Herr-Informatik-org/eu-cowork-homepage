Diese Seite listet jeden Container des Compose-Stacks mit Image, Aufgabe, Port und Profil.
Sie ist zum Nachschlagen gedacht, etwa wenn Sie eine Firewall-Regel schreiben oder wissen
wollen, warum ein Dienst nicht gestartet ist.

Alle Containernamen tragen ein Präfix aus der Variablen `STACK_NAME`, ohne Angabe lautet es
`eucowork`. Der Container des Chats heisst also standardmässig `eucowork-api`.

Odoo-Schlüssel. Der Schlüssel gehört zu einem eigenen Odoo-Benutzer, dessen Rechte im ERP die
Berechtigungsgrenze bilden.

<Aside type="caution" title="Drei Images laufen noch auf einem beweglichen Tag">
`searxng`, `rag_api` und das Interim-Panel `admin-panel` stehen auf `:latest`, während das
LibreChat-Image bewusst auf einen Digest gepinnt ist. Das ist ein offener Punkt und keine
begründete Ausnahme: Bei diesen drei Diensten kann ein `docker compose pull` also eine andere
Version ziehen als die zuletzt geprüfte. Warum ein fester Digest die bessere Wahl ist, steht
unter [Aktualisieren](/docs/betrieb/aktualisieren). Wer das jetzt schon vermeiden will, pinnt
die drei Images in `distribution/docker-compose.yml` selbst auf einen Digest.
</Aside>

## Welche Ports gehören nach aussen

Nur drei: **22, 80 und 443.** Alles andere bleibt lokal.

| Port | Dienst | Begründung |
|---|---|---|
| 22 | SSH | Administration |
| 80 | Caddy | Ausstellung der Zertifikate und Weiterleitung auf HTTPS |
| 443 | Caddy | Chat, Admin-Panel und Outlook-Add-in |

Caddy ist der einzige Dienst, der auf allen Schnittstellen lauschen darf. Das Admin-Panel und
das Outlook-Add-in sind bereits ab Werk an `127.0.0.1` gebunden. Die Datenbank, der
Suchindex, das Gateway und sämtliche Konnektor-Brücken sind gar nicht auf dem Host
veröffentlicht, sie sind ausschliesslich im internen Docker-Netz erreichbar.

Zwei Punkte müssen Sie selbst beachten:

- **Der Chat-Port ist standardmässig auf `0.0.0.0` gebunden.** In Produktion gehört
  `API_BIND=127.0.0.1` in die `.env`, sonst ist LibreChat unverschlüsselt unter
  `<server-ip>:3080` erreichbar, an Caddy und TLS vorbei.
- **Das Übergangs-Panel des Profils `interim` bindet auf allen Schnittstellen.** Es ist ein
  Testwerkzeug und gehört nicht auf einen erreichbaren Server.

<Aside type="danger" title="Die Firewall greift bei Docker-Ports nicht">
Von Docker über `ports:` veröffentlichte Ports umgehen `ufw`, weil Docker eigene
iptables-Regeln in der Kette `DOCKER-USER` schreibt. Ein auf `0.0.0.0` gebundener Container
ist trotz aktiver Firewall von aussen erreichbar. Der Schutz liegt in der Bindung an
`127.0.0.1`, nicht in der Firewall-Regel.

Wo eine Regel wirklich nötig ist, etwa bei den Debug-Ports des gehärteten
Code-Interpreter-Substacks, muss sie in dieselbe Kette:

```bash
sudo iptables -I DOCKER-USER -p tcp -m multiport --dports 3112,2000,3190,13000 ! -s 127.0.0.1 -j DROP
```

Der Interim-Interpreter (Port 8000) braucht das nicht: sein `setup.sh` bindet ihn an
`127.0.0.1` und prüft die Bindung nach dem Start nach. Bei einer Instanz, die vor dieser
Änderung aufgesetzt wurde, gilt das erst nach einem erneuten Lauf von `setup.sh`; bis dahin
bleibt die Regel für Port 8000 nötig.
</Aside>

## Die Docker-Netze

Der Stack verwendet zwei Netze.

| Netz | Art | Wer hängt drin |
|---|---|---|
| `default` | Bridge mit festem Subnetz aus `DOCKER_SUBNET`, Vorgabe `172.28.0.0/16` | alle Dienste des Stacks |
| `sandbox` | externes Netz aus `SANDBOX_NETWORK`, Vorgabe `eucowork-sandbox` | nur `api`, dazu der getrennte Code-Interpreter-Stack |

Das Sandbox-Netz wird bewusst ausserhalb des Stacks angelegt, damit beide Compose-Projekte
unabhängig voneinander starten und stoppen können. `install.sh` legt es an. Fehlt es, meldet
Compose beim Start, das als extern deklarierte Netz sei nicht auffindbar. Der Befehl dazu:

```bash
docker network create eucowork-sandbox
```

Das feste Subnetz ist Absicht. Kollidiert es mit einer Route, die ein VPN auf die Maschine
schiebt, brechen die ausgehenden Verbindungen der Container. Dann tragen Sie in der `.env`
einen freien Bereich in `DOCKER_SUBNET` ein.

<Aside type="caution" title="Mehrere Instanzen auf einer Maschine">
`STACK_NAME`, `DOCKER_SUBNET` und `SANDBOX_NETWORK` gelten Docker-weit und müssen deshalb pro
Instanz eindeutig sein. Dasselbe gilt für die Host-Ports `PORT`, `ADMIN_SIDECAR_PORT` und
`OFFICE_ADDIN_PORT`. Zwei Instanzen am selben Sandbox-Netz würden im schlimmsten Fall im
Code-Interpreter des jeweils anderen Kunden landen.
</Aside>

## Healthchecks

Healthchecks haben nur die Konnektor-Brücken, also die drei Odoo-Instanzen und
`ninjaone-mcp`. Sie fragen alle 30 Sekunden den eigenen Gesundheitsendpunkt ab, mit fünf
Sekunden Zeitlimit und drei Versuchen. Die Anlaufzeit beträgt 20 Sekunden für die
Odoo-Brücken und 15 Sekunden für die NinjaOne-Brücke.

Alle übrigen Dienste haben keinen Healthcheck. In `docker compose ps` erscheinen sie deshalb
als `Up` ohne Gesundheitsangabe, das ist kein Fehler. Ob die Anwendung wirklich sauber
gestartet ist, sehen Sie im Protokoll:

```bash
docker compose logs -f api
```

Die NinjaOne-Brücke bringt zusätzlich einen eigenen Selbsttest mit. Er prüft die
Zugangsdaten, die tatsächlich gewährten Berechtigungen, den Lesezugriff und dass schreibende
Pfade blockiert werden:

```bash
docker compose --profile internal run --rm ninjaone-mcp node src/selftest.js
```
