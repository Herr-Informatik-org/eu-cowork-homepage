Für einen Kunden mit wenigen Personen ist eine eigene virtuelle Maschine Verschwendung: Die
Grundlast einer Instanz ist gering. Mehrere Instanzen dürfen sich deshalb eine Maschine teilen.
Diese Seite beschreibt, wo dabei die Trennlinie verläuft. Sie richtet sich an IT-Dienstleister,
die mehrere Kunden betreiben.

## Die Mandantengrenze ist die Instanz, nicht die Maschine

Ein Kunde ist genau **eine Instanz**: eigene Datenbank, eigene Volltextsuche, eigene Uploads,
eigene Konfiguration, eigene Geheimnisse, eigenes Backend für die Code-Ausführung. Das ist
nicht verhandelbar und folgt direkt aus der Architektur: Die Anwendung selbst kennt keine
Mandanten. Die Trennung muss deshalb unterhalb der Anwendung liegen, und dort liegt sie sauber.

Ob zwei Instanzen dieselbe Maschine teilen, ist danach eine Kosten- und Risikofrage, keine
Architekturfrage mehr.

## Was nie geteilt wird

| Bereich | Grund |
|---|---|
| Datenbank | Enthält Konten, Konversationen und Buchungen eines Kunden |
| Uploads und Bilder | Kundeninhalte |
| Konfiguration und alle Geheimnisse | Ein gemeinsames Geheimnis hebt jede Trennung auf |
| Backend für die Code-Ausführung | Die einzige Stelle, an der Code von Nutzenden läuft |
| Inferenz-Schlüssel | Mit einem geteilten Schlüssel sind die Kosten pro Kunde nicht mehr auflösbar |
| Eigene Metasuchmaschine | Sieht die Suchanfragen und damit Nutzerinhalte |

## Was geteilt werden darf

- **Docker-Images und deren Schichten.** Das ist der grösste Spareffekt: Die Images werden nur
  einmal vorgehalten.
- **Ein vorgelagerter Reverse-Proxy** als einziger Dienst, der die öffentlichen Ports hält.
- **Host-Monitoring, Backup-Planung und automatische Sicherheitsaktualisierungen.**

Geteilt werden zwangsläufig auch Kernel, Docker-Dienst und die Hardware-Ressourcen. Das ist die
eigentliche Grenze dieser Betriebsart: Ein Neustart wegen eines Kernel-Updates trifft alle
Kunden der Maschine.

<Aside type="caution" title="Die Code-Ausführung ist der harte Punkt">
Überall sonst führt die Plattform nur eigenen Code aus, Nutzende haben keinen Zugang zur
Kommandozeile. Die Ausnahme ist die Code-Ausführung. Sie bekommt deshalb pro Instanz ein
eigenes, getrenntes Backend. Auf einer geteilten Maschine ist zudem die gehärtete Variante die
bessere Wahl.
</Aside>

## Was pro Instanz eindeutig sein muss

Mehrere Instanzen auf einer Maschine kollidieren, wenn sie sich Namen oder Adressen teilen.
Jede Instanz braucht deshalb einen eigenen Projekt- und Datenbereich sowie eigene
Netzwerk- und Portzuweisungen. Welche Werte das im Einzelnen sind und wie sie gesetzt werden,
steht im Betriebshandbuch. Bleiben sie auf den Standardwerten, startet die zweite Instanz nicht.

## Wann eine eigene Maschine

- **Kleine Kundschaft:** mehrere Instanzen auf einer gemeinsamen Maschine, je nach Grösse drei
  bis fünf Kunden.
- **Mittlere Kundschaft:** eine eigene Maschine pro Kunde.
- **Grosse Kundschaft, regulierte Branche, vertraglich zugesicherte dedizierte Infrastruktur
  oder eigener ERP-Anschluss:** eine eigene, entsprechend dimensionierte Maschine.

Die konkreten Richtwerte für Arbeitsspeicher, CPU und Plattenplatz stehen unter
[Systemanforderungen](/docs/erste-schritte/systemanforderungen).

## Betrieb mit mehreren Instanzen

- **Backup pro Instanz.** Jede Instanz sichert genau ihre eigenen Daten, mit versetzten
  Uhrzeiten.
- **Update pro Instanz.** Kunden dürfen unterschiedliche Versionen fahren. Genau dafür sind die
  Versionen fest gepinnt, siehe [Aktualisieren](/docs/betrieb/aktualisieren).
- **Monitoring.** Die erste Grenze ist der Plattenplatz, nicht der Arbeitsspeicher. Ein Alarm
  ab 70 Prozent Belegung ist sinnvoll, ebenso die Überwachung auf Dienste, die neu starten.
- **Offboarding.** Instanz stoppen, Archiv ziehen, Daten löschen. Kein Eingriff in andere
  Instanzen, keine Aufräumarbeit in einer gemeinsamen Datenbank. Das ist der eigentliche Gewinn
  der Instanzgrenze.
