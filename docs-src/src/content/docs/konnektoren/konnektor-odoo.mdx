Mit dieser Anbindung beantwortet der Chat Fragen zu Kunden, Belegen, Projekten, Mitarbeitenden und Zeiterfassung direkt aus Ihrem Odoo. Diese Seite beschreibt den Aufbau, die Einrichtung und die eine Betriebsregel, die man dabei nicht vergessen darf.

<Aside type="note" title="Nicht im Auslieferungszustand">
Die Odoo-Anbindung ist im Kunden-Template nicht enthalten. Sie ist Teil der internen Konfiguration und wird pro Instanz bewusst eingeschaltet. Der Auslieferungszustand einer neuen Installation enthält **keinen** vorkonfigurierten Konnektor.
</Aside>

## Wie die Anbindung aufgebaut ist

Der wichtigste Punkt zuerst: **Das Odoo-Modul spricht selbst kein MCP.** Das Modul `mcp_server` aus dem Odoo-App-Store stellt lediglich eigene Routen unter `/mcp/*` bereit, die über einen API-Schlüssel im Kopf der Anfrage abgesichert sind und nach innen mit Odoos gewöhnlicher Schnittstelle arbeiten. Ein Chat-System kann damit nichts anfangen.

Dazwischen läuft deshalb eine **Brücke**, ein eigener kleiner Dienst, der MCP auf der einen Seite spricht und Odoo auf der anderen. Wir verwenden dafür das fertige Image `ivnvxd/mcp-server-odoo`, auf Version `0.7.1` festgelegt. Die Kette sieht so aus:

```text
Chat-Schicht
  → MCP-Gateway            Rechteprüfung pro Aufruf, Protokoll
    → Odoo-Brücke          hält den API-Schlüssel, übersetzt MCP in Odoos Schnittstelle
      → Ihr Odoo           Enabled Models, Rechte und Record Rules des Schlüssel-Benutzers
```

Die Brücke hat **kein eigenes Anmeldeverfahren** und hält den API-Schlüssel. Deshalb liegt sie ausschliesslich im internen Docker-Netz und bekommt niemals einen Port auf dem Host. Die Zugangskontrolle macht das Gateway davor.

## Drei Instanzen, drei Dienstkonten

Es laufen **drei Instanzen derselben Brücke** nebeneinander: `odoo-administrator`, `odoo-admin` und `odoo-technik`. Sie sind technisch identisch und unterscheiden sich in genau einem Punkt: Jede benutzt einen **eigenen Odoo-API-Schlüssel**, und jeder dieser Schlüssel gehört einem **eigenen Odoo-Benutzer**.

Das ist der Kern des Konzepts. Ein API-Schlüssel in Odoo erbt vollständig die Rechte und die Record Rules seines Benutzers. **Der Odoo-Benutzer hinter dem Schlüssel ist damit die eigentliche Berechtigungsgrenze**, nicht der Prompt und nicht die Konfiguration. Wenn ein Odoo-Benutzer eine Lohnabrechnung nicht sehen darf, dann sieht sie auch der Chat über diesen Schlüssel nicht, unabhängig davon, was das Modell versucht.

Drei Instanzen statt einer bedeuten deshalb drei Rechteprofile, zwischen denen Sie pro Person wählen können. Das Gateway entscheidet, wer welche Instanz sieht.

| Instanz | Gedacht für |
|---|---|
| `odoo-administrator` | das weiteste Profil, etwa Geschäftsleitung |
| `odoo-admin` | kaufmännisches Profil |
| `odoo-technik` | technisches Profil ohne kaufmännische Sicht |

Welche Rechte diese drei tatsächlich haben, legen Sie in Odoo fest, nicht bei uns. Die Namen sind nur Etiketten.

## Nötige Variablen

Alle Werte gehören in `distribution/.env` auf dem Server. Diese Datei ist von der Versionsverwaltung ausgenommen und wird vom Installer auf `600` gesetzt. Hier stehen nur die Namen, niemals Werte:

| Variable | Zweck |
|---|---|
| `LIBRECHAT_CONFIG_FILE` | wählt die Konfigurationsdatei, in der die Konnektoren definiert sind |
| `ODOO_URL` | die Basis-Adresse Ihres Odoo |
| `ODOO_DB` | der Name der Odoo-Datenbank, wird bewusst nicht automatisch erkannt |
| `ODOO_MCP_API_KEY_ADMINISTRATOR` | Schlüssel des ersten Dienstkontos |
| `ODOO_MCP_API_KEY_ADMIN` | Schlüssel des zweiten Dienstkontos |
| `ODOO_MCP_API_KEY_TECHNIK` | Schlüssel des dritten Dienstkontos |

Die drei Schlüssel lassen sich alternativ im Admin-Panel unter **Einstellungen → API-Schlüssel** hinterlegen. Sie sind dort write-only, werden also nie wieder angezeigt. Der Sidecar schreibt sie in genau diese `.env`. Danach müssen die Brücken neu gestartet werden, weil sie ihren Schlüssel beim Start lesen.

## Einrichtung

<Steps>
1. **Drei Odoo-Benutzer anlegen** und jedem das gewünschte Rechteprofil geben. Danach je einen API-Schlüssel erzeugen unter **Einstellungen → Benutzer & Unternehmen → Benutzer**, den Benutzer wählen, Reiter **API-Schlüssel**, **Neu**.

2. **Erreichbare Modelle freigeben** unter **Einstellungen → MCP Server → Enabled Models**, jeweils getrennt nach Lesen, Schreiben, Anlegen und Löschen.

   Diese Freigabe gilt **instanzweit**, sie unterscheidet also nicht zwischen Ihren drei Dienstkonten. Die Unterscheidung machen allein die Rechte und Record Rules der drei Odoo-Benutzer.

3. **Werte in `distribution/.env` eintragen**, siehe Tabelle oben.

4. **Stack mit dem passenden Profil starten:**

   ```bash title="Auf dem Server"
   cd ~/eu-cowork/distribution
   docker compose --profile internal up -d
   ```

5. **Prüfen, dass die drei Brücken laufen.** Alle drei haben einen eingebauten Gesundheitscheck, `docker compose ps` zeigt den Zustand. Genauer geht es so:

   ```bash title="Auf dem Server"
   docker compose logs -f odoo-mcp-administrator odoo-mcp-admin odoo-mcp-technik
   docker exec eucowork-odoo-mcp-administrator python -c "import urllib.request;print(urllib.request.urlopen('http://localhost:8000/health',timeout=3).read())"
   ```

   Das Präfix `eucowork` im Containernamen stammt aus der Variable `STACK_NAME`. Läuft auf der Maschine mehr als eine Instanz, tragen die Container ein anderes Präfix.

6. **Rechte setzen, sofort.** Admin-Panel → **MCP-Zugriff**, für **jede** der drei Instanzen den **Server-Standard** auf verweigert stellen und speichern. Danach gezielt Rollen, Gruppen oder einzelne Personen freigeben.

7. **Chat-Schicht neu starten**, damit der Werkzeug-Katalog aktualisiert wird:

   ```bash title="Auf dem Server"
   docker compose restart api
   ```
</Steps>

<Aside type="danger" title="Pro Person genau eine Instanz freigeben">
Alle drei Instanzen exponieren **identische Werkzeugnamen**. Gibt eine Person zwei Instanzen frei, landet derselbe Werkzeug-Katalog zweimal in jeder Konversation. Das kostet doppelte Kontext-Tokens bei jeder Nachricht, und das Modell muss zwischen zwei gleich benannten Werkzeugen raten, was zu falschen Aufrufen führt.

Geben Sie deshalb pro Person **genau eine** Odoo-Instanz frei. Braucht jemand ein anderes Profil, wechseln Sie die Freigabe, statt eine zweite hinzuzufügen.

Denken Sie ausserdem daran, dass das Gateway ohne Regeldokument durchlässt. Solange der Server-Standard nicht auf verweigert steht, sehen alle Personen alle drei Instanzen.
</Aside>

## Welche Werkzeuge es gibt

Die Werkzeuge dieser Anbindung stammen aus dem **fremden Image**, nicht von uns. Ihre genauen Namen und ihr Umfang hängen deshalb von dessen Version ab, und wir dokumentieren sie hier bewusst nicht, weil sie sich mit einem Versionswechsel ändern können.

Sie sehen die tatsächlich vorhandenen Werkzeuge an zwei Stellen. Erstens im Verbindungstest unter **Konfiguration → MCP-Server**, der die Anzahl meldet. Zweitens, sobald sie benutzt werden, im Panel unter **System → Audit-Log**, Reiter **MCP-Tool-Calls**, Spalte Werkzeug. Dort steht pro Aufruf, welches Werkzeug von wem mit welchem Entscheid aufgerufen wurde.

Fachlich deckt die Anbindung die üblichen ERP-Objekte ab: Kunden, Belege, Projekte, Mitarbeitende und Zeiterfassung. Das Vorgehen im Chat ist mehrschrittig: erst den Datensatz suchen, dann gezielt lesen. Das ist in den Server-Instruktionen hinterlegt, zusammen mit der Regel, dass schreibende Aktionen immer zuerst der Person zur Bestätigung vorgelegt werden.

## Empfehlungen für den Betrieb

**Halten Sie die Enabled Models lesend.** Das ist die schärfste und zugleich einfachste Grenze. Ein Werkzeug kann nur so viel, wie Odoo für dieses Modell freigegeben hat. Wenn Schreiben, Anlegen und Löschen dort gar nicht angehakt sind, kann kein Modell und kein Prompt daran etwas ändern. Schalten Sie Schreibrechte nur für einzelne Modelle frei, für die Sie den Anwendungsfall wirklich haben.

**Ziehen Sie die Datengrenze in Odoo, nicht im Prompt.** Werkzeuge dieser Art nehmen häufig freie Filterausdrücke entgegen. Eine Einschränkung auf Argumentebene ist damit nicht verlässlich durchsetzbar. Verlässlich sind die Record Rules des Odoo-Benutzers hinter dem Schlüssel.

**Nutzen Sie das Protokoll.** Jeder Aufruf über das Gateway wird unveränderlich mitgeschrieben, ohne Löschfrist. Damit ist im Nachhinein belegbar, wer wann welche ERP-Daten abgefragt hat.

**Bedenken Sie, dass Odoo den einzelnen Chat-Nutzer nicht kennt.** Alle Personen mit derselben freigegebenen Instanz sehen dasselbe, nämlich das, was das jeweilige Dienstkonto sieht. Wenn Sie eine feinere Trennung brauchen, ist der Weg nicht ein zusätzlicher Filter im Chat, sondern ein weiterer Odoo-Benutzer mit engeren Rechten und eine weitere Instanz der Brücke.
